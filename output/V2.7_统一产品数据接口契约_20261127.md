# V2.7 统一产品数据接口契约（草案 0.1.0）

状态：**草案，未批准**；仅供官网与 Codex 销售系统后续对接讨论。
Schema：`src/website-v2/contracts/product-api.schema.json`

## 一、边界

- 本契约只定义**产品主数据 + 官网营销内容**的交换格式。
- 不包含库存、订单、价格、收款、客户与线索数据；这些系统不得因本契约重复建设。
- `products.json` 当前为 **local-candidate**，不是企业最终主数据库。`sourceOfTruth.kind` 在所有者书面批准前必须保持 `local-candidate`。
- 不直接修改 Codex 项目数据库。对接方式只能是导出/只读接口，具体由所有者决定。

## 二、统一主数据 vs 官网营销内容

| 类别 | 字段 | 归属 | 修改权限 |
| --- | --- | --- | --- |
| 主数据 | productId、sku、barcode、category、segment、flavor、packSize、ingredients、nutrition、feeding、target、companyFacts | 企业统一主数据 | 品牌方 + 配方/质检/GS1 核验后 |
| 主数据（证据） | evidence[].id/status、dataVersion、reviewStatus、publishStatus、updatedAt | 企业统一主数据 | 审核流程 |
| 官网营销 | headline、description、seoTitle、seoDescription、claims、media.alt | 官网内容 | 市场人员，但不得覆盖主数据 |
| 媒体 | media.images、media.video | 共享资产 | 需版权与实物核验 |

规则：

1. 营销层不得改写 `nutrition`、`feeding`、`packSize`、`barcode`、`target`。
2. `claims` 中任何认证/检测/配送承诺必须指向有效 `evidence` 条目；否则不得进入页面、API、SEO、AI 知识库或对外营销。
3. `publishStatus = blocked` 时，下游不得展示该产品的数值型内容（可展示名称/分类等身份字段）。
4. 多语言文本必须逐语言提供；缺失时回退规则由所有者批准，不得用其他语言冒充。

## 四、对接流程（建议）

1. 所有者批准主数据归属（官网本地候选 / Codex 数据库 / 新统一库）。
2. 由主数据方导出符合本 Schema 的 JSON；官网只读消费。
3. 发布前校验：`publishStatus=approved`、`reviewStatus=reviewed`、`barcode.status=verified`、`feeding.status=verified`。
4. 任何字段变更带 `dataVersion` 与 `updatedAt`；官网保留上一版本用于回滚。
5. 线索/订单不进入本契约，避免与 Codex CRM 重复。

## 五、安全与合规

- 接口不得包含 API Key、邮箱密码、客户个人信息。
- 传输仅 HTTPS；只读凭证最小权限；日志脱敏。
- 认证/检测类字段必须附 `evidence`；GCP/GLN 不得被解释为质量认证。
- 未批准数据不得进入搜索引擎结构化数据或 AI 知识库。

## 六、待所有者决策

1. 统一主数据归属（三选一）。
2. productId 命名规范是否采用 `pp-{species}-{flavor}-{segment}`。
3. 多语言缺失回退规则。
4. 是否需要对外公开只读 API（当前无此需求，默认不公开）。
