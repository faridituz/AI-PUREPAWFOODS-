## 四、数据管理“后台”如何工作（无独立数据库）

```text
包装 docx / PDF / logo
        │ 人工提取 + 记录来源
        ▼
content/products.json   ← 唯一数字源（营养/喂食/占比/规格/来源）
content/evidence.json   ← 素材状态（5 类）
content/content-log.json← 变更日志（全部 approved:false）
content/{lang}.json     ← 只放标签与文案，不放数字
        │ build.mjs（启动即校验格式与完整性）
        ▼
output/prototypes/{a,b,c,d}/…  +  content-status.json（待办清单）
        │ qa-data.mjs（逐页逐语言反向比对）
        ▼
发布审批（人工）→ 才允许 publicApproved:true
```

- **格式门禁**：产品必须 9 项营养、喂食表行列非空、含动物性原料占比与规格；缺一项直接构建失败。
- **一致性门禁**：`qa-data.mjs` 对 4 主题 × 8 语言 × 7 SKU 逐页抽取表格，与 `products.json` 逐值比对；不同语言出现不同数值会直接失败（当前 1,925 项 0 失败）。
- **草稿门禁**：`products.json` 与 `content-log.json` 有 `draft/publicApproved/approved` 标记，构建输出 `content-status.json` 汇总缺失与冲突。
- **缺失提醒**：每次构建把 missing/review 条目写入 `content-status.json`，不需要另开后台。
- **版本记录**：内容变更写入 `content-log.json`，代码与内容一起进 Git；回滚按提交回滚。
- **权限边界**：不存价格、库存、订单、客户资料；不连接 ERP/CRM/销售系统，因此**不重复核心销售系统的数据库**。
- **未来对接**：如接入 ERP，只读导出 `slug / EAN / 名称 / 净重 / 营养 / 喂食`，以 slug+EAN 为键回填本管线；价格与库存仍留在销售系统。

## 五、产品内容审批流程（建议执行）

1. 内容录入：从包装文字稿录入，附来源路径，状态 `draft`。
2. 内容复核：核对数字与包装是否一致，处理冲突，状态 `reviewed`。
3. 母语审校：每种拟上线语言由母语人员确认术语与语气。
4. 项目所有者批准：确认包装/证书/政策可公开。
5. 发布：将对应语言 `publicApproved` 改为 `true`，重建并跑全部 QA；生产部署另行批准。

当前没有任何条目走到第 4 步。

## 六、如何使用

| 目的 | 操作 |
| :--- | :--- |
| 查看待办缺失 | `output/prototypes/content-status.json` |
| 查看素材来源与状态 | `src/website-v2/content/evidence.json` |
| 修改营养/喂食 | 只改 `content/products.json`，重建；禁止在语言文件里改数字 |
| 新增产品 | 先在 `core/content.mjs` 的 `PRODUCTS` 注册 slug/分组，再补 `products.json`、各语言 `site.json.products` 与素材来源 |
| 校验 | `node src/website-v2/qa-data.mjs`（需本地服务 4173） |
